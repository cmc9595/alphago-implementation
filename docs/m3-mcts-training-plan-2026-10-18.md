# M3 Pro 36GB 한 대의 MCTS 공동 학습 계획

작성: 2026-10-18. 계획 문서이며 이 문서 작성으로 신규 장시간 작업을 실행하지 않았다.

## 목표와 출발점

SL 정책 final.pt + 10월16일 value_own/best.pt로 시작해, 탐색 방문 분포로 정책을, 실제 종국 승패로 가치를 개선한다. 두 망의 trunk까지 학습하되 현재 별도 구조를 먼저 유지한다. 빠른 롤아웃·외부 GPU·KataGo 교사 라벨은 추가하지 않는다. 실패한 첫 파일럿 후보를 다음 생산자로 채택하지 않는다.

기력 상승은 보장할 수 없다. MSE 감소와 기력 상승은 별도로 검증하며 사람 기준 단급은 이 계획의 대국 승률만으로 부여하지 않는다.

## 실제 기준 측정

출처: runs/experiments/search_iteration_400_20261018/run.log 및 iteration_001/*.json.

- 16판, 평균311수. 각 수 MCTS400회, batch32, 별도 정책/가치망, 단일 게임 순차 진행.
- 자가대국 합계1,245.26초(20분45초), 평균77.83초/판. 최솟값55.42초, 최댓값141.63초.
- 평균0.2503초/수, 계산 방문 처리 약1,598회/초. 이 값은 이 실행의 평균이며 다른 국면/전력/동시 작업에서 보장되지 않는다.
- 학습12판3,734국면/검증4판1,242국면, 234업데이트(약2epoch), 18.37초.
- 검증 가치 MSE0.7873에서1.0853으로 악화. 정책CE2.4142에서2.3477로 개선. 기존 엔진과 동일400회10판5승5패, 기력 향상 증거 없음.
- 학습흑백승수6:6, 검증2:2. 단순한 흑백 결과 수 불균형은 아니었다. 다만 검증4판으로 통계적 안정성을 확보하지 못했다.
- 새 가중치에 이전 BatchNorm 통계만 넣어 같은 검증 국면을 재평가해 MSE1.0288. 통계 변화만으로 전체 악화를 설명할 수 없다. 실제 가중치·서버는 바꾸지 않은 진단이다.
- 10판 평가의 탐색 연산합598.45초(판당59.85초). 계가/준비 시간은 별도.
- 16판 NPZ압축 합2,210,924바이트. 저장크기는 새로운 설정에서 다시 측정한다.

학습 연산보다 서로 다른 대국 경험 생성이 병목이다. 작은 자료를 반복 학습해서 GPU를 채우는 것을 목표로 하지 않는다.

## 1단계: 안정적인 데이터·학습·재개 지원

먼저 기존 파일럿 코드를 아래 범위로 확장한다. 현재 코드가 이미 지원한다고 표현하지 않는다.

- generation-only, train-only, evaluate-only 명령을 분리. 생산 모델 두 개의 SHA256/설정/난수 시드/규칙을 각 기보에 기록.
- selfplay 정상종료·상한·계가실패 및 판정시간을 기록. 상한/실패는 양쪽 head 학습에서 제외.
- 전체 기보는 저장하되 학습 표본은 명시적 ply 인덱스로 관리한다. 기보 단위 고정 train/dev/test 분리, 상한/실패로 유효 판수가 줄면 최소 유효 수 충족 전 학습 금지.
- 학습 배치의 국면은 먼저 서로 다른 게임을 뽑고 각 게임에서 국면 하나씩 선택. 동일한 한 국면만 영구 고정하는 것이 아니라 배치마다 다른 국면을 뽑는다. 긴 판에 과한 가중치를 주지 않는 선택이며 KataGo의 정확한 복제는 아니다.
- 단계별·게임별 평균 가치 MSE, 정책CE, 정책KL, 소유권MSE, 예측 승률 변화 기록. 불확실성은 국면 독립 가정 대신 게임 단위 bootstrap으로 추정.
- 50~100업데이트마다 validation과 model/optimizer/RNG 저장. 학습 악화 시 이전 후보 유지. 최종 test는 후보 선정 전 반복 사용하지 않는다.
- GPU 작업은 생성/학습/평가 중 하나씩만. CPU GNU Go 판정은 최대1개 다음 판과 겹쳐 실행하는 것을 추후 측정할 수 있다.
- 단일 GPU 모델 인스턴스, 기존 MPS비율0.12와 CPU RSS8GiB 점검 유지. 이는 시스템 전체 OOM 방지의 하드 보장이 아니다. 재생자료는 디스크 저장 및 제한된 LRU 캐시로 로드하고 전체를 float32로 미리 펼치지 않는다.
- 정전/프로세스 중단 시 완료기보 재사용, 마지막 원자적 체크포인트에서 재개. 잠자기 구간은 ETA에서 별도 표시.

## 2단계: 초기 자료 512판을 먼저 확보

기존 SL+value_own을 고정한다. 초기 기본안은 이미 검증한 균일400회/수이며, 512판(학습384/dev64/test64)을 먼저 모은 뒤 가중치를 바꾼다. 각 기보의 모든 저장 국면을 학습 후보로 활용할 수 있지만 배치 내 게임 중복과 반복 제시량을 제한한다.

실측 평균77.83초/판 단순 환산: 128판2.77시간, 512판11.07시간, 1,000판21.62시간. 이 시간은 중단 없이 기존 실행 속도가 유지된다는 가정이며 신뢰구간이나 완료 보장이 아니다. 실제 계획은 512판 생성에 약11~14시간의 여유를 잡고 첫32판에서 재산정한다.

25%확률로800회, 나머지100회인 KataGo식 탐색량 혼합은 자원 효율 비교용 후보이다. 평균예산275회=0.25*800+0.75*100으로, 균일400회의68.75%다. 비용이 탐색량에 선형 비례하면512판7.61시간이지만 이는 미측정 산술 예상이다. 100회는 현재 기본400회보다 낮은 별도 설정이다. 무조건 이 설정으로 전환하지 않고 소규모 속도/대국품질 비교를 거친다.

혼합 설정에서는 깊은 탐색 국면만 두 head의 학습 후보로 기록하고 빠른 수는 잡음 없이 진행한다. 루트탐험 설정/방문 정답을 분리한다. 빠른 수의 사활 실수와 승패 뒤집힘이 두드러지면 균일400회로 유지한다. 노이즈가 방문 분포를 바꾼 것만으로 정책 향상을 주장하지 않는다.

평균311수 가정 시512판 약159,232국면이며, 25%선택 시 약39,808개 학습후보가 남는다. 판 수는 같으므로 서로 다른 결과 경험은 늘지 않는다. 혼합안의 장점은 같은 계산 예산에 더 많은 판을 생성할 수 있다는 점이다.

## 3단계: 작게 이어 학습하고 후보를 선택

초기화는 기존 SL 정책 + 기존 value_own. 실패한 후보에서 이어가지 않는다.

- 두 망을 함께 업데이트하되 초기 policy/value lr를 각각0.0001 수준으로 시험한다. 이전 파일럿0.0005/0.001보다 작은 실험 시작값이며 검증된 최적값은 아니다.
- 최초 업데이트 예산은 새로운 학습 후보 수 대비0.25~0.5회분 표본 제시. 전체버퍼2epoch를 매번 반복하지 않는다. 기본배치32,64는 메모리를 측정한 뒤 비교.
- 균일400회의 학습384판은 평균약119,424후보이므로 배치32에서약933~1,866업데이트에 해당한다. 혼합800/100에서25%만저장하면약29,856후보로약234~467업데이트다. 실제 예산은 실제 유효 표본 수로 계산한다.
- 처음에는 BatchNorm running stats를 고정한 미세학습과 통계 재보정안을 dev에서 비교한다. 통계를 재보정할 때는 훈련 자료만 사용한다. 이것만으로 과적합이 해결된다고 가정하지 않는다.
- 소유권가중치1.5는 우선 유지해 변수 수를 제한. 정책 KL anchor는 현재 채택된 생산 정책으로 두어 한 번의 과도한 이탈을 제한하고, 영원히 최초SL만 모방하도록 만들지는 않는다.
- 후보0(미학습)도 항상 비교에 포함하고, dev 게임 평균/중반 성능을 보며 중간 체크포인트를 선택. 기존 RL자료 MSE와 새로운 MCTS자료 MSE의 절대값을 직접 비교하지 않는다.
- dev 가치MSE가 예를들어2%이상 악화하면 자동 적용을 보류하는 보수적 운영 기준부터 시작한다. 2%는 통계적 유의성이나 이론적 기준이 아니라 초기 guardrail이다. 실제 개선 판단에는 게임 단위 오차범위와 대국 결과를 함께 사용한다.

## 4단계: 데이터 창을 늘리며 제한된 학습 반복

처음 후보를 검증한 후,128~256판을 추가 생성할 때마다 후보 업데이트를 허용한다. 생산자는 마지막으로 채택된 정책/가치 쌍이다. 검증에 실패한 후보로 바로 자료를 만들지 않는다.

- 학습량은 새로 추가된 학습후보 수의0.25~0.5배 제시량으로 시작하고, 기존 replay에서 섞어 뽑는다. 최근2,000~5,000판 정도의 디스크창을 초기운영후보로 삼되 초반에는 버퍼를 먼저 늘린다.
- 기존 train/dev/test 게임은 역할을 영구 유지하고, 후보 데이터 생성기·탐색 설정 변경도 기록한다.
- 같은 초기자료로 계속 후보를 만들지 않는다. 후보 개선이 정체되면 학습 횟수를 늘리기보다 새 대국·탐색깊이·라벨품질을 점검한다.
- 후보 학습마다 대규모 대국 평가를 하지는 않는다. dev가 통과한 유망 후보를4번 정도의 데이터 추가 주기마다 모아 선별 평가한다.

## 5단계: 동일 탐색 횟수로 승급 결정

기존 채택 엔진과 후보 엔진은 모두400회/수, 같은 탐색배치/파라미터, 잡음 없는 대국, 동일 포석 흑백 교대. 생성시에800/100을 썼더라도 평가양쪽은400회로 통일한다.

- 20판은 큰 퇴보와 오류 선별용이며 실력 상승을 확정하지 않는다.
- 유망 후보는100판(50개 포석짝), 애매하면200판까지 확장. 포석짝 단위 신뢰구간도 확인한다.
- 단순히51승49패라고 승급하지 않는다. 예를들어100판60%이상이고 짝 단위 신뢰구간 하한이50%를 넘는 경우를 초기 채택 기준으로 사용한다. 이는 작은 향상을 놓칠 수 있는 보수적 선택이다. test자료가치판단과 고정사활국면도 확인한다.
- 현재 실측 연산량으로100판탐색만약1.66시간,200판약3.32시간. 실운영은 계가/준비/다른 사용을 포함해 약2시간/4시간 이상의 여유가 필요할 수 있다.
- 10판마다 후보를 바꾸는 대신 새기보수백판과 신뢰할만한 승급판정을 우선한다. GUI 모델은 명시적 교체 단계에서만 갱신한다.

## 이후에만 시도할 속도 개선

학습 방향이 검증되면 단일모델 인스턴스로4개 대국을 번갈아 진행하며 여러 트리의 leaf를 모아 GPU배치를 구성한다. Python프로세스마다 신경망을 복제하지 않는다. 1/4/8대국과batch16/32/64를 벤치마크해 결정하고4배속을 가정하지 않는다. virtual loss 중복률·정책분포 변화·실제방문수도 확인한다.

공유 trunk 정책/가치망으로의 증류는 다음 최적화다. SL trunk와 value_own trunk는 가중치가 달라 하나를 단순 복사하면 다른 head의 의미가 깨질 수 있다. 두 기존망을 교사로 사용한 별도 증류·평가가 필요하다. 먼저 별도구조에서 개선을 확인하고 이후 동일시간 처리량과 동일탐색 기력을 함께 검증한다.

C++ MCTS 재작성, 신경망 확대,8방향전수평가,매수50,000회,16판마다전체망교체는 초기 우선순위에서 제외한다. 기존 rollout제외범위는 유지한다.

## 첫 실행 순서

1. 데이터전용/학습전용분리,재개,게임별배치/검증,중간저장기능부터 구현·테스트.
2. 필요하면32판 규모로 균일400과800/100혼합의 속도/기보품질을 비교. 혼합설정의 비용추정은 이때 교체.
3. 선택한 설정으로512판누적,384/64/64게임분리. 기존16판은 개발용이므로새test에넣지않음.
4. 기존두망에서저학습률로0.25~0.5회분미세학습,후보0포함dev선정.
5. 유망후보동일400회20판선별→100~200판검증,통과후생산자갱신.
6. 이후128~256판추가와제한학습을반복.누적약1,000판에서도개선신호가없으면정지하고원인재진단.
